# Getting Started

## Entry Identity

- Name: Getting Started
- Version: 1
- Canonical Identifier: tiinex.core.entry.getting-started.v1
- Entry Family: tiinex.guided-entry.native.v1
- Human Label: Getting Started

## Purpose And Scope

- Purpose: Help someone unfamiliar with Tiinex begin ordinary useful work with the smallest truthful amount of structure, using the qualified environment and the person's actual goal.
- In Scope: first-use orientation-to-work transition, readable explanations, relevant capability discovery, Workspace association, proportionate artifact selection, qualified authoring when appropriate, preserving recoverable progress.
- Out Of Scope: preselecting tasks, auto-creating Projects, Roles or Processes, inferring Workspace ownership, assigning participants, automatic deployment, publication, acceptance or remote mutation.

## Entry Context

- Entry Target: a first-use session where the participant wants to start something new with an available qualified Workspace or Tiinex environment.
- Required Context: qualified initial Start/bootstrap and Workspace projection when a carrier exists; selected runtime and its actual available content sources; the person's expressed intention and applicable authority limits.
- Relevant Context: the current, qualified Docs Workspace material at `.topics/documentation/getting-started/001-getting-started.trace.md`, including its bounded first-use guides when that material is actually supplied; the selected runtime's `catalog`, `schema-guide` and schema/companion content; governing Business work boundaries, if relevant.
- Context Exclusions: mere presence of a Workspace, schema, guide, Role, Process, or host target does not prove applicability, authority, identity, or work ownership. Unavailable Docs guidance is not silently replaced with an invented manual.

## Preparation

- Preparation Method: orient the supplied environment through qualified Tooling, then discover relevant available capabilities from the current runtime rather than a memorized list of built-in schemas. When the qualified Docs Getting Started material is available, use it for the pedagogical path and link to its detail only when needed.
- Reconciliation Policy: reconcile an identified ongoing project or governing work relationship before adding new work; if the user's new goal might be independent, preserve that distinction rather than choosing an arbitrary Parent.
- Discovery Breadth: begin with the smallest relevant Workspace and runtime catalog view, widening only when the goal or qualified ownership requires it. Unfamiliar imported schemas are eligible for consideration when present and qualified.
- Currentness Policy: treat qualified carried content and verified newer lineage as evidence; do not elevate a guide, filename, Status label, initial prompt, or arrival order over current schema and authority contracts.
- Uncertainty Policy: ask a single ordinary-language clarification when uncertainty changes where the work belongs or what may be preserved; otherwise start with a reversible, useful step and state what remains open.

## Entry Method

- Method: first help the person make progress on their requested goal. If the work becomes a continuing project, establish whether it belongs in the supplied Workspace, then independently select only useful qualified artifact types from the runtime catalog. Read their actual schema and companion guidance, use preflight/authoring and qualified Parent relationships, and create the smallest durable structure that helps. When progress needs to survive the session, choose a qualified Workspace checkpoint or Handoff according to actual continuation intent and authority. Explain outcomes in everyday language before internal terminology.
- Readiness Boundary: the participant can identify what they are making, what is being kept and why, and the next useful step; any created artifacts and saved carrier must be genuinely qualified. A pleasant first-use explanation alone does not prove durable continuity.
- Stop Conditions: if qualified context, schema material, Workspace relationship, or required authority cannot be established, avoid fabricated files or claims and clearly state the smallest missing requirement.

## Presentation And Interaction

- Intended Audience: first-time human Tiinex users, collaborating assistants and future host adapters.
- Presentation Guidance: respond to the person's own goal in simple terms, not a lecture on Tiinex. Introduce vocabulary only when it enables an immediate choice. Separate the useful creative/technical deliverable from Tiinex records that help preserve it.
- Interaction Guidance: ask what kind of work the person wants, then help. Do not require them to request a Task, Process, Workspace, schema, or Handoff by name. At meaningful save/resume boundaries offer a practical way to keep both files and their working context.
- Diagnostic Detail Policy: keep catalog mechanics, hashes, provenance diagnostics and internal schema labels secondary unless they materially affect confidence, progress, permissions or the user's question.

## Interpretation Limits

- Does Not Establish: that a session occurred, a Task is selected, a Workspace owns the new goal, a Role is assigned, a user is identified, a Process is applicable, or remote mutation and publication are authorized.
- Must Not Be Inferred: that the model's use of this Entry proves independent first-use acceptance or that every available artifact schema should be used.

## Portability Notes

- Portable Semantics: orient, discover, associate, act proportionately and preserve recoverable work without assuming the participant already understands Tiinex.
- Environment Assumptions: an applicable qualified content/runtime surface; if the host cannot write durable files or return a complete Workspace carrier, disclose that limit rather than simulating persistence.
- Non-Portable Details: particular CLI executable paths, GitHub API, host UI controls, ChatGPT, VS Code/Copilot model versions and transport-specific instructions.
