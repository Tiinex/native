# Multi-Material Evidence Versioning Qualification Boundary

## Supported Claim Or Question

- Supported Claim Or Question: What exact Native semantics must be qualified before one Evidence can contain two individually described material entries without losing older Evidence compatibility?
- Evidence Role: architecture probe, immutable-v1 constraint and owner-qualified candidate fixture; not a new operative Evidence schema.
- Review Context: Sigma expects `+ Add Material` with one file reference, kind and description per entry; the current Evidence form has two ordinary fields and concatenates links.

## Provenance

- Known Source: qualified Native `tiinex.evidence.v1` published-immutable-canonical binding and Schema Validation Contract, native owner Task `001-qualify-repeatable-evidence-material-entries.trace.md`, existing Core named-declaration contract, and the complete carried 17-Workspace Handoff Package.
- Preservation Basis: exact [experimental per-entry Native schema candidate](fixtures/repeating-evidence-material.contract-candidate.experimental.md) kept beside this Evidence with SHA-256 `2491984c9521003c730e62f6dea911a08e04143f795fc9f70c9b01dc7937b4e8`.
- Provenance Limits: the fixture is **not** a Tiinex schema, never receives a false publication commit, is not discoverable as a canonical schema, and must not be executed as a creation contract.

## Evidence Material

- Material Kind: source schema comparison and experimental owner-facing representation fixture.
- Material: current `tiinex.evidence.v1` (published immutable) exposes `## Evidence Material` with ordinary `Material` and `Material Kind`. Future repeated entries need stable local identity, independent reference/type/description/provenance/limits and shared Evidence claim/interpretation limits. The candidate describes first-level named declarations in `## Evidence Material` and versioned schema semantics; it does not assert that Native has approved any version or field names.
- Description: Core's already-qualified named-declaration machinery was mechanically tested using an existing registered session schema; two entries were created/validated independently, while duplicate names, missing mandatory fields and unbound fields failed closed. A separate Core schema-document parser probe accepts the candidate `Entry Shape` vocabulary. Neither result qualifies new Evidence metadata or runtime publication.

## Preservation And Fidelity

- Preservation State: exact candidate bytes retained unmodified under Native Task fixtures; published Native schema and runtime companions are unchanged.
- Fidelity Notes: never split legacy `Material` delimiters into independent entries automatically; doing so would misattribute per-entry meanings and source metadata.
- Known Losses: no concrete `tiinex.evidence.v2` Native module, schema-bound renderer, qualified source/binding, Core creation/projection, VS Code Add/Remove for Evidence or end-to-end re-open PASS.

## Interpretation Limits

- Not Yet Used As: schema approval, publication, form behavior or Windows acceptance.
- Does Not Prove: that existing Handoff/Session named-declaration semantics are automatically correct for evidence provenance or item identity.
- Must Not Be Treated As: authorization to mutate published v1 or to create a host-specific second validation engine.
- Need For Review: Native explicitly qualify a versioned material entry schema and inherited boundaries, Core bind/render/validate roundtrip for that exact schema, then generic host Add/Remove per item and Sigma acceptance. Preserve old v1 unchanged.
